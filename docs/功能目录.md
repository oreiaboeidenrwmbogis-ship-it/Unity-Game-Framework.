# Unity 独立游戏商业模板 — 功能目录与开发顺序

> 版本: v1.0 (2026-09-08)
> 定位: 长期维护的商业级、独立游戏标准项目模板，适配大部分游戏类型（2D/3D、动作/RPG/解谜等）
> 图例: ★ = 相对原稿新增；↻ = 对原稿的修正/补充
>
> 核心原则: 服务不继承 MonoBehaviour，由启动器统一 Tick；模块间只通过事件和接口通信；数据与逻辑分离；异步统一走 UniTask。

## 一、核心架构层（地基）

### 1.1 应用启动器 Bootstrap ★
- **职责**：唯一的启动场景，按依赖顺序初始化所有服务，并统一驱动它们的 Tick / Dispose。
- **要点**：
  - 所有服务实现统一接口 `IGameService { Init(); Tick(); Dispose(); }`，**不继承 MonoBehaviour**——场景里不允许有满天飞的 Update()。
  - 初始化顺序用依赖图表达（日志 → 事件中心 → 时间 → 场景 → 资源 → UI → 音频）。
  - 初始化失败可降级（资源挂了仍能进主菜单并提示），不能直接崩。

### 1.2 游戏状态机 Game State Machine ★
- **职责**：游戏级状态：`Boot → Splash → MainMenu → Loading → Gameplay → Pause → GameOver`。
- **关键认知**：**场景 ≠ 游戏状态**。主菜单、设置、背包是同一场景下 UI 栈的不同状态；Pause 是状态不是场景。
- **要点**：状态切换广播事件，各系统据此响应（暂停时音频压低、输入屏蔽）；切换是异步的（先 Loading 再进游戏）。

### 1.3 服务定位器 Service Locator ↻
- **职责**：全局服务注册/获取容器，消灭满天飞的 `GetInstance()`。
- **修正**：只允许启动阶段注册（运行期禁止，防隐式依赖）；测试时能注入 Mock；游戏逻辑优先构造注入 + 事件，别到处 `Get`。

### 1.4 事件中心 Event Bus ↻
- **职责**：全局事件总线，模块解耦命脉（击杀怪物 → 抛事件 → 任务/成就/统计各自监听，互不认识）。
- **修正**：**强类型事件**（struct + 泛型订阅），不要 string key——拼写错误编译期查不出来，长期必腐化。
- **要点**：订阅/退订、一次性监听、下帧触发、调试模式事件日志；**红线：对象销毁必须退订**，否则内存泄漏。

### 1.5 对象池 Object Pool ↻
- **职责**：GameObject 池 + 纯 C# 类池（泛型），覆盖子弹、特效、UI 节点、音频源。
- **补充**：预热（进战斗前批量生成）、池上限降级策略、`IPoolable { OnSpawn(); OnDespawn(); }`、统计接口（喂给调试面板）、延迟回收（粒子播完再回收）。

### 1.6 状态机框架 FSM ↻
- **职责**：通用状态机：玩家状态、敌人 AI、UI 面板状态。
- **补充**：`Enter/Exit/Tick` 基类；转换条件表驱动（状态 × 条件 → 目标）；支持分层 FSM（AI 顶层巡逻/追击/攻击，攻击下再分前摇/挥砍/后摇）；状态切换抛事件。

## 二、数据与资源层

### 2.1 资源加载 Asset Manager
- **职责**：Addressables 封装：异步加载（UniTask 风格）、引用计数、按 Label 分组加载/释放。
- **要点**：按关卡分组做内存预算（切场景整组释放，防止玩得越久内存越大）；本地 + 远程热更新双模式；**全面禁用 Resources.Load**。

### 2.2 静态配置表 Config System ↻
- **职责**：ScriptableObject + Excel/CSV 导入管线，配置物品、怪物、任务数值。
- **补充**：**代码生成**——Editor 工具从表结构自动生成强类型访问代码（`Configs.Item.Get(1001)`），杜绝手写 ID 字符串；导入时校验 ID 重复、引用缺失。
- **铁律**：数值改表不改码，代码里没有魔法数字。

### 2.3 存档系统 Save System ↻
- **职责**：多存档槽位、自动/手动保存、读档校验。
- **补充**：
  - 序列化：MessagePack（二进制，快小）或 JSON（可读）；建议存档用前者，开发期另输出 JSON 副本排查。
  - **版本号 + 迁移链 ★**：存档头带版本号，加载跑迁移（v1→v2→v3），老玩家读档不炸——长期维护的生命线。
  - AES 加密（单机防改只能增加成本）；`ISaveStorage` 接口预留云存档；读档损坏要能降级提示，不能白屏。

## 三、基础支撑层

### 3.1 输入系统 Input Manager ↻
- **职责**：New Input System 封装，硬件输入映射为逻辑指令（`Move/Jump/Interact`），代码只认逻辑指令。
- **补充**：运行时改键（联动设置系统保存）；自动识别键鼠/手柄，UI 提示图标切换；输入屏蔽走状态/事件，不用 enabled 硬开关。

### 3.2 场景流转 Scene Manager ↻
- **职责**：异步加载/卸载、进度上报、Loading 联动。
- **补充**：**场景参数传递**——加载后向场景注入上下文（读档进入、玩家在哪、身上有什么），场景不自己找全局变量；切换流程固定为「请求 → Loading → 卸旧 → 装新 → 初始化」，可取消可超时。

### 3.3 时间管理器 Time Manager ↻
- **职责**：全局时间缩放（子弹时间/暂停）+ 高精度 Timer。
- **修正**：**Timer 用手动 tick 驱动，不用 Coroutine**——天然支持暂停和缩放，还能区分「受缩放影响的计时器」（技能 CD）和「真实时间计时器」（加载超时）。
- **补充**：分层时间缩放（"只有玩家减速"），用 Channel 实现。

## 四、游戏系统层

### 4.1 UI 框架 ↻
- **职责**：栈管理全屏面板/弹窗（层级、遮罩、返回逻辑）+ MVC 分层。
- **要点**：UI 预制体走 Addressables；返回逻辑统一（Esc/手柄 B → 弹栈），不每个面板自己写；面板 Open/Close 事件供音频、输入屏蔽联动。
- **决策（ADR）**：UI 采用 **uGUI**（教程多、生态全、上手快；UI Toolkit 留作编辑器工具界面）。全项目统一，混用必乱。

### 4.2 音频系统 ↻
- **职责**：Audio Mixer 分层（Master/BGM/SFX/Voice）、独立音量、淡入淡出、SFX 走对象池。
- **补充**：BGM 播放列表/战斗音乐互切；同音效多变体随机播放防重复感；3D 音效挂对象池对象随行。

### 4.3 背包与物品系统 ↻
- **职责**：数据层（重量、堆叠、格子）+ 表现层（拖拽、拆分、快捷栏）+ 接口驱动（`IUsable/IEquippable/IStackable`）。
- **补充**：
  - **物品定义与实例分离**（定义=配置表静态数据，实例=数量/耐久动态数据）——背包系统经典架构，必须分清。
  - 操作全走统一 API（添加/移除/交换/拆分），UI 只是调用者。
  - 变化广播 `OnInventoryChanged` 事件，UI 订阅刷新而非轮询；背包状态接入存档。

### 4.4 任务系统 ↻
- **职责**：节点式状态（未接取/进行中/已完成/失败）。
- **补充**：任务目标抽象成 `ITaskObjective`（击杀 N 个/收集 N 个/到达位置），**靠监听事件中心计数**——任务系统不认识怪物代码；任务链/前置条件；任务定义进配置表，实例状态进存档。

### 4.5 对话系统
- **职责**：对话树节点图、选项分支、打字机效果。
- **要点**：数据用 ScriptableObject 节点图 + 条件分支；LLM 接口预留 `IDialogueProvider`（本地树实现 vs 远程 LLM 实现），UI 需做「思考中」状态。

### 4.6 本地化系统
- **职责**：Text/Image/Audio 多语言切换，运行时生效。
- **要点**：文本 Key 查表，缺 Key 回退英文 + 告警日志；切换广播事件，UI 自动刷新。

### 4.7 设置系统 Settings ★
- **职责**：画质、分辨率、帧率、音量、键位、语言的**唯一写入口**。
- **为什么必须有**：音量归音频管、键位归输入管——设置系统是它们的统一出口和存档载体，没有它设置界面没法做。
- **要点**：启动应用一次、修改即存档；泛型 `Set/Get`，新增设置项零改动框架。

### 4.8 成就/统计系统 ★
- **职责**：成就解锁、全局统计计数。
- **要点**：事件驱动的天然产物——监听事件中心计数（击杀/死亡），达阈值解锁 + 弹窗；平台 API（Steamworks）预留。

### 4.9 相机系统 ★
- **职责**：相机切换/混合、平滑跟随、屏幕震动。
- **要点**：直接集成 Cinemachine（官方免费），自写薄封装（震动用 Trauma 衰减模型）。**不要自研相机系统，性价比极低。**

### 4.10 特效管理器 VFX ★（轻量）
- **职责**：特效统一走对象池，`PlayVFX("key", pos, rot)` 一行播放、自动回收。

### 4.11 游戏内调试面板 Debug Console ★
- **职责**：FPS/内存/对象池活跃数/事件监听数/Timer 数实时显示；运行时作弊控制台（无敌、加钱、跳任务）。
- **为什么必须有**：性能问题可视化——卡顿时一眼看出是池泄漏还是 Timer 失控，对学习价值巨大。
- **要点**：Release 包用 scripting define 完全剔除。

## 五、工程化层（"商业级"真正分水岭）

### 5.1 自定义日志 ↻
- 分级（Debug/Info/Warn/Error）+ 颜色 + 打包后一键关闭 + Error 写文件（崩溃后可排查）。

### 5.2 扩展方法库
- Transform/Vector3/List 高频扩展。**克制**：只放真高频的，别堆一百个没人用的。

### 5.3 asmdef 模块化 ★
- 每个模块一个程序集（`Template.Core`、`Template.Inventory`...），**强制单向依赖**（背包能引用 Core，Core 不能引用背包）。
- 没有它，一年后代码互相引用成毛线团——这是「长期可维护」的技术底座。命名空间与 asmdef 一一对应。

### 5.4 测试框架 ★
- EditMode 测试（纯逻辑）：背包增删交换、存档读写迁移、事件订阅退订、配置表校验。
- PlayMode 测试：场景加载、UI 面板栈、对象池。
- CI：GitHub Actions + GameCI，提交自动跑。**长期维护靠测试回归，不靠记忆。**

### 5.5 构建发布管线 ★
- 一键打包脚本（BatchMode 命令行）：版本号管理、切 define（关日志/调试面板）、打包后校验。**打包必须是脚本，不能是"编辑器里点 Build"**——后者不可复现。

### 5.6 Editor 工具 ★
- 配置表编辑器/校验器、资源引用检查器、对象池统计窗口。Editor 代码单独 asmdef，不进运行时包。

### 5.7 Git 与目录结构 ↻
- 官方 .gitignore + Git LFS（美术音频大文件）；第三方插件进 `_ThirdParty/`，永远不改插件源码；目录按 `_Project/{Scenes, Scripts, Data, Prefabs, Art, Audio}` 划分。

## 六、技术选型（汇总）

| 领域 | 选型 | 说明 |
|---|---|---|
| 引擎 | Unity 2022.3 LTS（本工程实际版本 2022.3.62f3c1） | 当前 LTS 均可；如需后续升 Unity 6 影响面小 |
| UI | **uGUI**（2026-09-09 拍板） | 生态全、资料多；UI Toolkit 仅用于编辑器工具界面 |
| 异步 | UniTask（免费） | 商业事实标准，替代 Coroutine |
| 资源 | Addressables | 已定 |
| 输入 | New Input System | 已定 |
| 存档 | MessagePack + 版本迁移 | 二进制快小 |
| Tween | DOTween 免费版 | 几乎必备 |
| DI | VContainer（可选） | 先用 ServiceLocator 起步 |
| 寻路 | NavMesh + 薄封装 | AI 用 |

**可选扩展（不列入主线）**：网络抽象层（排行榜/云存档）、埋点分析、种子随机、HybridCLR 热更代码——等真实需求出现再做。

## 七、开发顺序

核心原则：**每个阶段都有可运行、可演示的产出；任何系统先有真实使用场景再写。一口气写完 = 过度设计陷阱。**

| 阶段 | 内容 | 依赖关系 | 产出（验收标准） |
|---|---|---|---|
| **0. 骨架**（1-2 天） | git 初始化、.gitignore、目录结构、asmdef 划分、命名空间、日志、扩展方法 | 无 | 空工程，编译通过 |
| **1. 核心循环**（1-2 周） | Bootstrap → 游戏状态机 → 事件中心 → 时间管理器 → 对象池 → 场景流转 | 日志先行（排错）；事件中心先行（其余模块都依赖它） | 能启动 → 主菜单 → 切场景 → 暂停的最小工程 |
| **2. 表现层**（1-2 周） | UI 框架 → 输入系统 → 音频系统 → 设置系统 | 依赖阶段 1 的事件中心；设置系统与输入/音频同期开发（互有依赖） | 完整主菜单 + 设置界面（音量/键位/语言可调） |
| **3. 资源与数据**（1 周） | Addressables 接入 → 配置表管线 → 存档系统（含迁移） | 配置表先行（背包/任务/本地化都要读它） | 资源异步加载 + 读档存档可用 |
| **4. 玩法系统**（2-3 周） | 背包 → 任务 → 对话 → 成就 → 相机 → 特效 | 全部依赖配置表 + 事件中心 + 存档；背包 UI 依赖阶段 2 的 UI 框架 | 用一个小 demo 游戏（如小型 ARPG）验证所有系统互相配合 |
| **5. 工程化**（持续） | 测试 → CI → 构建管线 → 调试面板完善 | 测试针对阶段 3/4 的重逻辑系统（背包、存档）补写 | 一键出包 + 提交自动回归 |

**顺序的深层逻辑**：
- 事件中心必须最先做——它是后面所有模块的通信总线，晚做就要返工。
- 背包、任务、成就全部建立在「配置表 + 事件 + 存档」之上，所以这三个底座（阶段 1、3）必须先行。
- UI 放在玩法之前，因为背包/对话/任务的表现层都是 UI。
- 测试放最后补，是因为没有真实系统可测时，测试就是空中楼阁——但阶段 3 之后每个新系统**必须同步带测试**，这是「专业独立开发者」和「Demo 级」的分界线。
